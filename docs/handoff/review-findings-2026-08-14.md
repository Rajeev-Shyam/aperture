OsSidecar::kill (lines 454-464) calls tokio Child::kill on the HOST process, which on Windows is TerminateProcess. The hosts' only mechanisms for reaping their GPU-holding child are kill_on_drop(true) on their own Child handle (crates/vlm-host/src/main.rs:216, crates/stt-host/src/main.rs:211) and a ctrl_c graceful-shutdown hook (stt-host main.rs:394-400) — neither runs when the host is TerminateProcess'd, and Windows does not kill children when a parent dies. ## [HIGH] [correctness] STT WAV-as-JSON blows axum's 2 MB default body limit — utterances over ~18 s always fail
crates/stt-host/src/main.rs:356

gpu_scheduler.rs's new STT arm (crates/orchestration/src/gpu_scheduler.rs:540) posts { "wav": Vec<u8> } as a JSON array of numbers, and stt-host's transcribe_handler uses axum 0.7's Json extractor with no DefaultBodyLimit override (no occurrence anywhere in crates/). Axum's default limit is 2,097,152 bytes. A 16 kHz mono 16-bit utterance is 32,000 WAV bytes/s, and after normalize_peak the byte values are near-uniform 0-255, serializing at ≈3.6 chars/byte ⇒ ≈114 KB of JSON per second of speech ⇒ the limit is crossed at ≈18 s. MAX_UTTERANCE is 30 s, so any held utterance whose trimmed speech exceeds ~18 s gets a 413 before the handler runs, which SidecarRunner maps to JobError::SidecarDown and the user sees 'transcription failed' with nothing in the stt-host logs. vlm-host /infer has the same construction (image_jpeg as a JSON byte array, vlm-host main.rs:94-96) and large desktop JPEGs can intermittently 413 into a silent OCR-only degrade. Relatedly, the SidecarRunner 30 s reqwest timeout (gpu_scheduler.rs:439) is marginal for CPU base.en on a near-30 s clip.

**Fix sketch:** Add .layer(DefaultBodyLimit::max(16 * 1024 * 1024)) to both hosts' routers now; longer term send the WAV/JPEG as base64 (≈1.33x) or raw bytes instead of a JSON number array.

**Verifier:** Verified end-to-end. gpu_scheduler.rs:540 posts the WAV as serde_json `{"wav": Vec<u8>}` — a JSON array of decimal integers. stt-host's /transcribe uses axum 0.7's Json extractor (main.rs:354-357) and no DefaultBodyLimit exists anywhere in the repo (grep: zero matches), so the 2,097,152-byte default applies and over-limit requests 413 before the handler runs. Voice pipeline confirmed 16 kHz mono i16 (32,000 WAV bytes/s, audio_capture.rs) with normalize_peak(0.9) on the trimmed buffer (lib.rs:279) spreading byte values to ~3.5 chars/byte serialized; even at a conservative 3.0 chars/byte the 2 MiB limit is crossed at ~22 s, well under MAX_UTTERANCE = 30 s (lib.rs:70). The 413 maps to JobError::SidecarDown at gpu_scheduler.rs:544-546 — a misleading failure with no stt-host handler log. vlm-host /infer has the identical construction (Json<InferRequest> with image_jpeg: Vec<u8>, main.rs:94-96, 404-406) and its arm doesn't even check status, so a 413 also degrades silently to SidecarDown/OCR-only.

## [MEDIUM] [correctness] Adaptive VAD discards continuous quiet speech with near-uniform frame RMS
crates/voice/src/vad.rs:103

speech_threshold sets threshold = clamp(3 × p20(frame RMS), 0.0004, 0.012). If the utterance has no genuinely quiet frames — user starts talking at/before key-down and speaks continuously, so the 20th-percentile frame is itself speech — then no frame reaches 3× the p20 unless the speaker's frame-to-frame dynamic range exceeds ~9.5 dB above the p20, and the SPEECH_RMS_CEILING rescue only applies to frames ≥ 0.012 RMS. On exactly the quiet mic this fix targeted (peaks ~0.9-1.5 % FS ⇒ speech RMS ≈ 0.003-0.005, far below 0.012), a monotone or continuous utterance yields first=None/last=None in trim() and the whole gesture is DiscardedTap regardless of length — re-creating the silent-PTT-death failure the adaptive gate was built to fix (now at least with the 'Didn't catch that' message). Degenerate case: perfectly uniform RMS at any level < 0.012 is ALWAYS all-silence since 3q > q.

**Fix sketch:** Cap the threshold relative to the utterance's own peak as well (e.g. threshold = min(3×p20 clamped, 0.5 × max frame RMS, 0.012)) so at least the loudest frames of a real utterance always qualify when they clear SPEECH_RMS_FLOOR.

**Verifier:** Confirmed against vad.rs:99-130 and lib.rs:252-279. The threshold is clamp(3×p20(frame RMS), 0.0004, 0.012) computed over the utterance's own frames, and trim() runs on RAW pre-gain levels (normalize_peak(0.9) is applied only after the tap gate, explicitly commented 'VAD already judged the raw levels'), so the quiet-mic premise (speech RMS ~0.003-0.005) holds where the threshold is evaluated. The math checks out exactly: (1) a frame qualifies only at ≥3×p20 ≈ 9.54 dB above the 20th-percentile frame, so if the quietest fifth of frames is itself speech (user talking at/before key-down, <20% gap frames in the hold), a low-dynamic-range utterance clears nothing; (2) the SPEECH_RMS_CEILING rescue only helps frames ≥0.012 RMS, unreachable on exactly the quiet mic this commit targeted; (3) the degenerate claim is exact — uniform RMS r < 0.012 always yields all-silence (r<0.004 → threshold=3r>r; 0.004≤r<0.012 → threshold=0.012>r). Result: first=None/last=None, speech_ms=0, DiscardedTap regardless of utterance length — re-creating the discarded-speech failure (now with user feedback, hence medium not high). mcp_bridge::spawn has an unavoidable window between server.connect() returning and ServerOptions::new().create(MCP_PIPE_NAME) standing up the next listener instance (src-tauri/src/mcp_bridge.rs:61-70). During that window a client CreateFile gets ERROR_PIPE_BUSY. call_app performs exactly one ClientOptions::open attempt and maps ANY error to 'Aperture is not running on this machine' — the tokio named-pipe docs specifically prescribe a WaitNamedPipe/retry loop for ERROR_PIPE_BUSY. Two near-simultaneous tools/call round-trips (a second Claude Desktop window, or a tools/call racing the previous connection's teardown) will surface a spurious, misleading 'not running' failure to the model.

**Fix sketch:** In call_app, loop on ERROR_PIPE_BUSY (os error 231) with a short sleep/deadline before giving up, and keep the 'not running' message only for ERROR_FILE_NOT_FOUND.

**Verifier:** CONFIRMED by reading both sides of the pipe. Client (aperture_mcp.rs:106-111): call_app performs exactly one ClientOptions::open attempt and map_err(|_| ...) collapses EVERY error — including ERROR_PIPE_BUSY (os 231) — into "Aperture is not running on this machine"; no retry loop exists anywhere in the binary. Server (src-tauri/src/mcp_bridge.rs:56-75): the accept loop hands the connected instance off and only THEN calls ServerOptions::new().create(MCP_PIPE_NAME), so between connect() returning and create() succeeding there is exactly one pipe instance and it is busy — Windows CreateFile in that state returns ERROR_PIPE_BUSY (not FILE_NOT_FOUND). Tokio's ClientOptions::open docs explicitly prescribe a sleep/retry loop for ERROR_PIPE_BUSY; tokio does not retry internally. Trigger requires two near-simultaneous clients (each tools/call opens a fresh connection, but one aperture-mcp process serializes its calls, and the server re-creates the listener while the prior call is still dispatching — so a lone Claude Desktop window essentially never hits it; a second window/MCP host racing the handoff does). Result is a spurious "not running" error surfaced to the model while the app is up. Severity "low" is correctly calibrated and the proposed fix (retry on os error 231 with a deadline, keep the not-running text for ERROR_FILE_NOT_FOUND) matches the documented pattern.
